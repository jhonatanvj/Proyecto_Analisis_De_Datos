# Workshop 3, Part 1: pipeline improvements and PySpark implementation

Source text for the report sections *Pipeline Improvements* and *PySpark Implementation*. Every change below starts from something we observed while running the Workshop 2 pipeline; numbers are from runs on 2026-11-19.

## 1. Pipeline improvements (before / after)

| # | Observed in Workshop 2 | Change | Effect |
|---|---|---|---|
| 1 | All Silver topics were written to one folder. `spark.read.parquet("datalake_silver/")` would merge five different schemas and also read the `_state/` files. | One folder per topic (`datalake_silver/<topic>/`); quarantine stays in `quarantine/`. `scripts/migrate_silver_layout.py` moves existing files. | Each topic is read as one DataFrame with one schema. The database loader keys files by name, so moved files were not loaded twice (checked: 12 moved, 0 reloaded). |
| 2 | The text corpus was the scraped Volcano Updates page: 9 records on 2026-11-16, 12 three days later. Too small for keyword or tone analysis. | New source `usgs_hans_notices`: the HANS notice search (`POST search/search`) returns 20 notices per page **with their full HTML**. Backfill of the archive since 2010 one month per Bronze file, then hourly incremental runs from a watermark. | 203 monthly Bronze files, 16,540 notices (the same count per year as the API's `preflight`), 16,535 in Silver: 2010-01 to 2026-11, six observatories (AVO 41 %, HVO 41 %, NMI, CVO, CalVO, YVO), eight notice types (daily updates 59 %, weekly updates 21 %...). Around 830 search pages, ~20 minutes. |
| 3 | Notice bodies are dominated by repeated text: contact e-mails, "Subscribe to these messages", link lists, the observatory mission paragraph. | Text step cuts the notice at the first footer marker, drops lines that are only a link, and extracts the *Summary* section (the `RMK:` line in a VONA). Alert level and colour code are read from the text; for multi-volcano notices the highest level is kept. | Footer words no longer reach the keyword counts. Each notice gets a short, comparable `summary_clean` for the tone analysis (Part 3). |
| 4 | FDSN was only a one-off backfill (radial query per volcano, 165+ requests). Revisions of past events were never seen again. | Incremental FDSN: `updatedafter=<watermark>` with one query per US volcanic region (6 boxes that contain all 169 volcanoes with a 30 km margin). The watermark is the newest `updated` stored in Bronze, advanced only after the file is written; each run starts 60 min earlier. | 6 requests and 3.4 s for a week: 2,622 events created **or revised**, among them revisions of 2018 and 2019 events. Silver keeps only events within 30 km of a volcano. |
| 5 | In the middle of the notice backfill (month 2019-12) the server answered HTTP 200 with a body that was not JSON; the same request worked a minute later. The HTTP retry policy does not cover that case and the run stopped. | The search client checks the body and repeats the request up to 4 times with a growing wait (5, 10, 20 s). POST is added to the retried methods (only read-only search endpoints are posted to). The backfill records finished months and skips them when started again. | The backfill resumed from 2019-12 without downloading the first 119 months again. |
| 3b | The first Silver pass over the archive showed four text problems: 96 % of the notices had no summary (the *Summary:* label only exists since ~2019; older notices say *Activity Summary for past 24 hours*, *Volcanic Activity Summary*, *Activity Update* or *Remarks*); header lines (alert level, colour code, coordinates, elevation, VNUM) made *current, level, code, color, aviation, ft, vnum* top tokens; the fixed *Background* (3,285 notices) and *Definitions of terms used* (1,982) paragraphs repeated the same words; and the ʻokina (written `, ʻ or ') split Hawaiian names into *halema / uma / pu*, while *kīlauea* and *kilauea* were counted apart. | Summary labels of every format plus a fallback (first narrative paragraph of 80+ characters); header lines and the fixed sections removed from the body; ʻokina removed inside words; tokens fold diacritics (text_clean keeps them); a domain stop-word list `config/stopwords_domain.txt` (units, months, weekdays, time zones, agency and notice words), the list Workshop 2 had planned. `scripts/reprocess_silver_source.py` rebuilds one source's Silver files after such a change. | Notices without a summary: 96.1 % → 0.2 %. Mean body length 3,800 → 2,781 characters (27 % repeated text removed). Top tokens before: *volcano, lava, summit, activity, crater, current, level, eruption, seismic, ft*; after: *volcano, lava, activity, summit, kilauea, crater, eruption, volcanic, seismic, satellite* and in the summaries *elevated, eruptive, unrest, detected*. |
| 3c | The notice identifier was taken as the key, but 708 identifiers appear twice: an activity notice (VAN) and its aviation version (VONA) are published with the same identifier and different text. Silver kept only one of each pair. | The key is identifier + notice type (`usgs_hans_notice:<id>:<type>`); `duplicate_key` in `sources.yaml` updated. | 708 notices that were dropped as duplicates are back (15,829 → 16,535 rows); one real copy (same id, type and text) is still removed. |
| 6 | Incremental sources with no new data would write empty Bronze files every hour. | `write_bronze` skips empty windows for `usgs_hans_notices` and `usgs_fdsn`. | Bronze only grows when something changed. |
| 7 | Workshop 2 stopped at Silver; the project database was a draft. | Silver → PostgreSQL loader: one transaction per Silver file (upserts by content hash, `ingestion_run`, `ingestion_state.watermark`, `silver_load_file`). | First load: 292,774 events in about 90 s; a second run loads nothing. |
| 8 | `event_group` was empty. A first matching query (self-join of all earthquakes on time and distance) ran for more than 5 minutes and was cancelled. | Two rules in `storage/event_groups.py`, parameters in `config/sources.yaml`: (a) *same quake, different network*: within 16 s, 10 km and 0.5 magnitude units, comparing each event with its next 3 in time through a window function; (b) *volcano week*: alert notices, eruptions and the earthquakes near that volcano in the same ISO week. | 11 s instead of minutes. Of 6,702 earthquake pairs within 16 s and 10 km, only 163 came from different networks; the other 6,539 are swarm events from one network, not copies, so the rule requires two networks. Result: 124 duplicate pairs (e.g. `hv61684461` / `us10008fuh`: same time, same place, M3.23 vs 3.2) and 948 volcano-week episodes (largest: Kilauea, week 37 of 2024, the September 2024 eruption with 396 nearby earthquakes). |
| 9 | The Postgres image runs `sql/` only when its volume is empty, so every new SQL file had to be applied by hand in each clone (003 and 004 were). | `db-migrate` service: on every `docker compose up` it applies each `sql/*.sql` that is new or changed (SHA-256 in table `schema_migration`), one transaction per file; `001` was made idempotent like the others, and the Airflow scheduler waits for it. | Tested on the existing database (4 files applied, data kept), on a second run (0 applied), on an empty database (full schema) and after editing three files (re-applied). `005` reached the database with no manual step. |
| 10 | The notice corpus only existed in Silver and Gold; the final dashboard must read from the database. | `sql/005_volcano_notice.sql` (own table: 985 region-wide notices have no volcano and no coordinates, which `event` requires) and the loader topic `notices`. | 16,535 notices loaded in 47 s, 14,650 linked to a catalogue volcano; a second run loads nothing. New hourly notices follow the same path automatically. |

Things that did not work, and why:

* `obsAbbr: "all"`, the value shown in the HANS documentation, returns 0 notices; an empty string returns all of them (16,539 since 2010).
* Guessed endpoint names such as `notice/getNoticesByVolcano` do not exist, and the documented notice endpoints only cover recent notices (`getRecentNotices`: the last month, 84 notices on 2026-11-19). The archive is only reachable through the search API.
* The HANS volcano list (`usgs_hans_volcanoes`) only feeds the transform context, but the Silver runner had no transform for it and quarantined its first Bronze file as `unknown_source`. Reference sources are now marked processed without a reject (one false row remains in the quarantine of 2026-11-19).
* Restarting Docker Desktop (to apply the new memory limit) brought the Airflow containers back with the image built before PySpark and psycopg were added; `load_to_database` failed with `No module named 'psycopg'` and kept retrying, which looked like a very slow Silver DAG. `docker compose up -d --build` recreates them; the README now says so.
* Spark 3.5 does not run on the Java 25 installed on one team laptop. Spark runs inside the Airflow image (Java 17), and the Spark tests skip themselves on a host without a supported Java.
* Docker Desktop had 3.7 GB of memory, not enough for Airflow plus a Spark driver; it was raised to 5 GB through `.wslconfig` (the laptop has 7.3 GB).

## 2. PySpark implementation

**Session** (`src/volcano_pipeline/gold/spark.py`): `SparkSession.builder.master("local[*]")`, settings from environment variables set in `docker-compose.yml`:

| Setting | Value | Why |
|---|---|---|
| `spark.driver.memory` | `SPARK_DRIVER_MEMORY`, 1g | In local mode the driver also runs the tasks; 1 GB fits next to Airflow in 5 GB. |
| `spark.sql.shuffle.partitions` | 8 | The default 200 is meant for clusters; the largest topic (~300k rows) fits in 8. |
| `spark.ui.enabled` | false | No port is published for it. |
| `spark.sql.session.timeZone` | UTC | Every Silver timestamp is UTC. |
| `spark.sql.parquet.datetimeRebaseMode*` | CORRECTED | GVP eruptions go back to the Holocene; dates before 1582 are read as proleptic Gregorian instead of failing. |

**Docker**: the Airflow image installs `default-jre-headless` (Java 17 on Debian 12, also on ARM) and sets `JAVA_HOME=/usr/lib/jvm/default-java`; `pyspark` is pinned to 3.5.4 by the Airflow 2.10.5 constraints file.

**Reading Silver**: `spark.read.parquet("datalake_silver/<topic>/")` per topic (`gold/silver_reader.py`), the same call that reads a cloud storage prefix.

**DAG** `gold_processing` (weekly, Monday 03:00 UTC): `check_silver` (skips when Silver is empty) → `build_governance` → `build_storytelling`. The two builders run one after the other, each with its own SparkSession, so two JVMs never share the container memory. Full run on the real data (~292k earthquakes): about 4.5 minutes.

**Output contract** (`gold/contract.py`): both summaries are one long table `section, metric, dimension, period, value, unit, generated_utc`. Builders return any DataFrame with `section, metric, value`; `conform()` adds the optional columns, casts the types and stamps the run time. The file is written with `coalesce(1)` to a temporary folder and its single part file is renamed to `datalake_gold/<kind>_YYYYMMDD_HHMMSS.parquet`, which pandas reads directly in Workshop 4.
